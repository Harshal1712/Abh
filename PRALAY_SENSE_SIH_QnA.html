System Overview & Problem Statement
Q1 What problem does PRALAY-SENSE solve and why is it important?

PRALAY-SENSE addresses the lack of an integrated, explainable, expert-assisted multi-hazard intelligence layer for flood and landslide prediction in Northeast India — specifically Assam.

  • Assam experiences recurring floods and rainfall-triggered landslides every monsoon season.
  • Existing systems are hazard-specific (flood-only or landslide-only) and rarely explainable.
  • Raw geospatial data (satellite imagery, rainfall grids) is rarely translated into actionable community alerts.
  • AI-only systems risk false alarms or missed events without human expert validation.

Our approach: Fuse multi-source satellite + terrain + rainfall data through dedicated AI models, route predictions through an expert review gate, and dispatch only expert-approved alerts to communities.

💡 Tip: Emphasise the Expert-in-the-Loop design — this is your unique differentiator from pure AI solutions.
Q2 What is the geographic scope of your prototype?

The current prototype focuses on the state of Assam, India — specifically targeting districts in the Brahmaputra Valley and Barak Valley most frequently affected by floods and landslides.

  • DEM used: Copernicus GLO-30 at 30m resolution, covering all of Assam.
  • Landslide susceptibility baseline raster generated using historical NRSC/ISRO inventory data.
  • Default map center: (26.14°N, 91.73°E) — Assam.

Future scope: Scale to Northeast India → Pan-India.

Q3 What makes your system different from NDMA / IMD existing warning systems?
  • Multimodal fusion: SAR + optical + terrain + real-time rainfall — not just rainfall alone.
  • Explainability: Ranked feature attribution showing which factor drove the risk score.
  • Multi-hazard: Single platform for flood + landslide.
  • Expert Gate: Every AI prediction reviewed and approved before public alert.
  • Citizen feedback loop: Community ground-truth reports feed back into validation.

IMD and NDMA issue region-wide advisory bulletins without location-specific, explainable AI-driven predictions.

💡 Tip: Frame it as complementary — "We fill the last-mile gap between global products and local community action."

Data Sources & Satellite Imagery
Q4 What satellite data do you use and how is it accessed?
  • Sentinel-1 (SAR — C-band): Provides VV and VH backscatter. We compute temporal change (VV-change, VH-change) to detect inundation. Accessed via Copernicus Data Space.
  • Sentinel-2 (Optical — MSI): Provides NDVI, NDWI, MNDWI, NDBI, BSI spectral indices. Accessed via Copernicus Data Space.
  • DEM (GLO-30): NASA/ESA Copernicus 30m DEM. Derives slope, aspect, TRI, TPI for terrain analysis.
  • Rainfall: Open-Meteo API — hourly past 31 days + 4-day forecast. Computes 24h, 3d, 7d, 14d, 30d cumulative windows.
Q5 How do you handle cloud cover — a major issue during monsoon?

We handle it with a two-pronged strategy:

  • Primary: Sentinel-1 SAR is our main sensor. SAR is an active microwave sensor — it penetrates clouds and rain, giving reliable data when optical sensors are obscured.
  • Secondary: When Sentinel-2 is available (clear sky), we enrich the model with spectral indices. CatBoost handles missing S2 features gracefully using default values.
  • Rainfall: Obtained from Open-Meteo weather API, completely unaffected by cloud cover.
💡 Tip: Always lead with SAR when answering cloud-cover questions — it is your strongest technical argument.
Q6 What is GSMaP and did you actually use it?

GSMaP (Global Satellite Mapping of Precipitation) is a JAXA/ISRO satellite-based rainfall product giving near-real-time gridded rainfall at 0.1° resolution.

In our prototype: We use Open-Meteo API as our live rainfall source (which aggregates ERA5 reanalysis + NWP models). The PPT mentions GSMaP as an intended production data source.

The architecture is designed to swap in GSMaP or IMD gridded data — weather_service.py is a pluggable data adapter.

💡 Tip: Say: "Our prototype uses Open-Meteo; the production system will integrate GSMaP-ISRO directly via MOSDAC API."
Q7 What spatial resolution does your DEM have and why does it matter?

We use the Copernicus GLO-30 DEM at 30-metre spatial resolution covering all of Assam.

From the DEM we derive: Slope (primary landslide driver), Aspect (moisture retention), TRI (terrain ruggedness), TPI (ridge vs valley identification).

30m resolution is sufficient for district/village-level hazard zonation. For higher precision, CARTOSAT-1 (2.5m) DEM from NRSC could be substituted.

3
AI & Machine Learning Models
Q8 Which ML model did you use and why CatBoost specifically?

We use CatBoost (Categorical Boosting) — a gradient boosted decision tree framework by Yandex.

  • Handles mixed numeric features and missing data natively without imputation.
  • Provides built-in Global Feature Importance for our Feature Attribution panel.
  • Significantly faster inference than deep learning — critical for real-time map click response.
  • Proven performance on tabular geospatial feature sets (DEM + rainfall + SAR).
  • We have two separate models: landslide_catboost_v2_s2.cbm and a flood CatBoost model.
💡 Tip: Mention: "We compared with Random Forest and XGBoost — CatBoost gave the best F1 score on our validation set."
Q9 What features does your model use for prediction?

Landslide CatBoost V2 — 31 features total:

  • Terrain (5): DEM elevation, slope, aspect, TRI, TPI — from GLO-30 rasters.
  • Rainfall (1): 24-hour forecast rainfall from Open-Meteo.
  • Sentinel-2 Spectral Indices (6): NDVI, NDWI, MNDWI, NDBI, BSI, EVI.
  • Sentinel-1 SAR time series (19): VV/VH backscatter values across multiple acquisition dates.

Flood model features: DEM, slope, Sentinel-1 VV/VH change, rainfall windows (1d/3d/7d), soil moisture.

Q10 How did you train the model? What was your training dataset?
  • Positive samples: Historical inventory from NRSC/ISRO Landslide Atlas of India — georeferenced landslide polygons across Assam and Northeast India.
  • Negative samples: Randomly sampled stable terrain points, matched by elevation range to avoid geographic bias.
  • Feature extraction: For each sample, DEM derivatives, historical S1/S2 indices, and rainfall from the corresponding time period.
  • Balanced class weighting to address imbalanced disaster data.
  • Temporal holdout validation — trained on pre-2023 events, tested on 2023-2024 events.
  • Metrics: F1-score, Recall, PR-AUC (not accuracy — disasters are rare events).
Q11 What is your model accuracy? What are its limitations?

Our model outputs a probability score (0–1). Limitations we openly acknowledge:

  • Model generalization: Trained primarily on Assam data — may need retraining for other geologies.
  • Temporal resolution: Rainfall is hourly but DEM/terrain is static.
  • No real-time S2 ingestion: In prototype, S2 indices use latest available scene.
  • Class imbalance: Landslides are rare — we use oversampling and class weighting.

This is why the Expert-in-the-Loop gate exists: the model flags risk, a human validates before any alert is sent.

💡 Tip: Judges appreciate intellectual honesty about limitations — it shows maturity and real understanding.
Q12 How does multi-hazard risk fusion work?

We run flood and landslide models independently for the same coordinate, then fuse:

  • If flood risk ≥ threshold OR landslide risk ≥ threshold → Primary Hazard = MULTI_HAZARD.
  • Combined Priority = max(flood_priority, landslide_priority) with escalation logic.
  • Confidence = weighted average of model-reported confidence metrics.

In Assam, high rainfall events trigger both flooding in valleys AND landslides on slopes simultaneously. A compound event is more dangerous than either alone.

Q13 What is Feature Attribution / Explainability in your system?

We use CatBoost's built-in Global Feature Importance to show which input features most influenced a prediction:

  • The AI Risk Analysis page shows ranked cards: e.g., Slope → 45%, Rainfall → 30%, SAR Change → 15%.
  • Makes the AI decision transparent to the expert reviewer — they can judge if the reason is valid.
  • For production: We plan to integrate SHAP (SHapley Additive exPlanations) for local (per-prediction) attribution — more precise but computationally heavier.
💡 Tip: Point to the "Key Contributing Factors" panel in your demo. Judges love explainable AI answers.

System Architecture & Tech Stack
Q14 Explain your system architecture — how do all components talk to each other?

We use a 3-tier microservices architecture:

  • Frontend (React + Vite): Expert dashboard + citizen portal + Leaflet map. Makes REST API calls to Node.js backend.
  • Backend (Node.js + Express + MongoDB): Stores risk events, alerts, reports. Orchestrates expert workflow. Sends Twilio + Nodemailer alerts.
  • Python ML Service (FastAPI + Uvicorn): Runs CatBoost inference. Reads GeoTIFF rasters. Fetches live weather. Exposes /risk, /flood, /explanation.

Flow: User clicks map → Frontend → Node backend → Python ML → rasters + weather → risk JSON → MongoDB → rendered UI.

Q15 Why Node.js for the backend instead of Python/Django?
  • Separation of concerns: Python handles computation-heavy ML. Node.js handles I/O-bound tasks (database, webhooks) — each optimised for its role.
  • Non-blocking I/O: Node's event loop handles multiple concurrent requests from expert + citizen portals simultaneously.
  • Rich ecosystem: Twilio, Nodemailer, Mongoose, Cloudinary all have excellent Node.js support.
  • TypeScript: Full type safety across frontend and backend.
Q16 Why FastAPI and not Flask?
  • Async support: FastAPI is ASGI-based — critical since we use async httpx for weather API calls alongside rasterio reads.
  • Performance: FastAPI + Uvicorn is significantly faster than Flask's synchronous WSGI server.
  • Automatic API docs: Auto-generated OpenAPI/Swagger documentation.
  • Pydantic validation: Request/response models are validated automatically.
Q17 How do you handle concurrent requests to the ML service?

This was a real challenge we solved during development.

  • Problem: Rasterio's global dataset readers are not thread-safe. Concurrent requests to the same 1.92 GB raster file caused deadlocks and connection aborts.
  • Solution: We initialise global raster handles at startup (init_raster()) and keep them open. The /risk and /flood endpoints are designed to be independent — they never call each other.
  • Production plan: Process pool with separate raster handles per Uvicorn worker.
💡 Tip: This shows real engineering problem-solving — judges will be very impressed if you explain this concurrently challenge.
Q18 How is data stored? What is your database schema?

We use MongoDB (NoSQL) via Mongoose for flexible schema evolution.

  • RiskEvents: lat/lng, flood/landslide probability, terrain features, S1/S2 data, confidence, status (PENDING_REVIEW → APPROVED/REJECTED), rejection reasons.
  • CommunityAlerts: Approved alerts — multilingual messages, affected area, expiry, dispatch status.
  • CommunityReports: Citizen ground-truth — photo URL, description, coordinates, hazard type.

MongoDB chosen because geospatial risk event schemas evolve rapidly during R&D — NoSQL gives schema flexibility without migrations.

Expert Review & Alert Dispatch Workflow
Q19 Walk us through the complete lifecycle of an alert — from AI prediction to community dispatch.
  1. Detection: Expert clicks map location → parallel calls to /risk + /flood endpoints.
  2. Assessment: Python ML reads terrain rasters, fetches live rainfall, runs CatBoost, returns probability + feature attribution.
  3. Event Creation: Expert reviews Point Query Analysis and clicks "Create Risk Event". Saved to MongoDB with status PENDING_REVIEW.
  4. Expert Review: Expert opens Expert Decision Panel. Reviews AI rationale, feature importance, SAR/S2 data. Chooses: APPROVE / MODIFY / HOLD / REJECT.
  5. Alert Generation: On APPROVE, CommunityAlert created with multilingual messages (English, Hindi, Assamese).
  6. Dispatch: Expert publishes → Twilio WhatsApp + Gmail notifications sent to citizens in affected radius.
  7. Validation: Citizens submit ground-truth reports → expert reviews → feeds back into confidence scoring.
Q20 What happens when an expert rejects an event? Is the reason recorded?

Yes. When an expert clicks "Reject Event", a modal dialog asks for a mandatory rejection reason (e.g., "False positive", "Outdated imagery", "Ground truth verified safe").

  • Rejection reason is stored in MongoDB alongside the event — creating a full audit trail.
  • Rejected events show in Active Events page with status REJECTED and reason displayed.
  • Patterns in rejection reasons guide model retraining and threshold calibration.
Q21 How do you ensure no false alarms reach the public?

Three layers of safeguards:

  • Layer 1 — Confidence Threshold: Low-confidence events flagged as LOW priority, requiring additional evidence.
  • Layer 2 — Expert Gate: No alert ever sent without explicit expert sign-off. System cannot auto-publish.
  • Layer 3 — Alert Preview: Expert sees a "Mobile Citizen Preview" showing exactly what the citizen will receive before publishing.

Experts can also MODIFY the AI-generated alert message before approval.

6
Citizen Portal & Community Feedback
Q22 How does the citizen portal work?
  • View active hazard alerts for their area in real time.
  • Submit ground-truth reports: Upload a photo, enter description, select hazard type, auto-detect or manually enter location.
  • Photo upload stored via Cloudinary CDN; metadata (coordinates, timestamp, type) in MongoDB.
  • EXIF geolocation extracted from uploaded photos automatically using the exifr library.

Reports are reviewed by experts and used to validate or challenge AI predictions.

Q23 How do citizen reports improve the system over time?
  • If citizen reports active flooding where AI predicted LOW risk → expert investigates and recalibrates confidence thresholds.
  • Accumulated verified reports → growing labelled dataset for model retraining.
  • Reports are timestamped and geotagged — enabling temporal analysis of disaster evolution.

This creates a feedback-driven improvement loop: AI predicts → expert validates → citizens confirm → data improves → model retrains.

Q24 What languages are your alerts available in?
  • English — primary technical alert language.
  • Hindi (हिंदी) — for Hindi-speaking officials and citizens.
  • Assamese (অসমীয়া) — primary local language of Assam, ensuring last-mile reach.

Each language version is editable by the expert before dispatch, allowing contextual localisation beyond direct translation.

Future scope: Add Bengali, Bodo, and other Northeast Indian languages.

Feasibility, Scalability & Real-World Impact
Q25 Is this system feasible to deploy at scale? What are the compute requirements?
  • Python ML Service: Requires GPU or multi-core CPU server. AWS EC2 g4dn or Azure NC-series suitable.
  • MongoDB: MongoDB Atlas (cloud-managed) supports horizontal sharding.
  • Raster data: GeoTIFFs hosted on AWS S3 + served via Cloud Optimized GeoTIFF (COG) for efficient partial reads.
  • Cost estimate: For Assam-scale deployment (~1000 events/monsoon) — cloud costs ~₹2,000–5,000/month.
Q26 How does your system handle areas with no internet / low connectivity?
  • Pre-computed baseline raster: Landslide susceptibility raster stored locally — no internet required per query.
  • SMS alerts: Twilio SMS works on basic cellular networks — no smartphone or data needed for the citizen to receive the alert.
  • Batch processing: Risk assessments can run in batch mode (daily via node-cron) rather than on-demand.
  • Future: Edge deployment of CatBoost model on NDMA field devices.
Q27 What is your plan for scaling from Assam to Pan-India?
  • Phase 1 (Current): Assam — flood + landslide. Core architecture validated.
  • Phase 2: All Northeast India — expand raster coverage, add district-level calibration.
  • Phase 3: Pan-India — integrate NRSC national DEM, add regional model variants.
  • Phase 4: Multi-hazard expansion — earthquake, cyclone, drought, forest fires.
  • Phase 5: IoT integration — river gauge sensors, weather stations, NDMA IDRN API.

The microservices architecture makes this modular — each hazard is a separate ML service behind the same expert review pipeline.

Q28 How is your system better than simply using Google Flood Hub or Copernicus EMS?
  • Flood Hub: Primarily river gauge-based flood forecasting — not terrain + SAR multi-hazard.
  • Copernicus EMS: Activated only after a disaster is declared — not a predictive system.
  • Neither provides: Local language alerts, citizen feedback loop, expert review gate, or explainable AI attribution.
  • Both are global products not calibrated for Assam's specific hydrology and terrain.
💡 Tip: Frame it as complementary: "We fill the last-mile gap between global products and local community action."
Q29 What is the expected time from AI prediction to community alert?
  • Map click → risk result: 3–8 seconds (dominated by weather API call + raster read).
  • Event creation → expert review: Near-instant (in-app notification).
  • Expert review → alert approval: Design target < 15 minutes.
  • Alert dispatch (WhatsApp + Gmail): < 30 seconds via Twilio/Nodemailer.
  • Total end-to-end: < 20 minutes from AI flag to citizen alert.
Q30 What is the societal impact of your system?
  • Early warning: Even 1–3 hours of advance notice enables evacuation of vulnerable populations.
  • Resource optimisation: Identify high-risk roads and infrastructure — pre-position NDRF teams.
  • Reduced false alarms: Expert gate prevents alert fatigue (the "cry wolf" problem).

Quantified impact potential (Assam):

  • Assam floods affect ~2.5 million people annually (ASDMA data).
  • Landslides in Assam Hills — 100+ deaths/year in recent monsoons.
  • Even 50% lead time improvement could save hundreds of lives annually.

Rapid-Fire Technical Definitions (Q31–Q50)
QuestionAnswer
Q31. What does SAR stand for?Synthetic Aperture Radar — active microwave sensor that works day/night regardless of cloud cover.
Q32. What is NDVI?Normalized Difference Vegetation Index = (NIR − Red) / (NIR + Red). Measures vegetation health; drops near flooded/disturbed areas.
Q33. What is TRI?Terrain Ruggedness Index — measures terrain heterogeneity. High TRI = rough terrain = higher landslide risk.
Q34. Why CatBoost and not a Neural Network?Faster, more interpretable, better on tabular data, doesn't require GPU for inference.
Q35. What is SHAP?SHapley Additive exPlanations — game-theory-based method for explaining individual model predictions. Planned for production.
Q36. What port does your ML service run on?Port 5001 (FastAPI + Uvicorn).
Q37. What port does your backend run on?Port 5000 (Express.js).
Q38. What database do you use?MongoDB (via Mongoose) — NoSQL document store.
Q39. How do you send WhatsApp alerts?Twilio WhatsApp API — requires Twilio account with WhatsApp sandbox enabled.
Q40. How do you send email alerts?Nodemailer with Gmail SMTP using App Passwords.
Q41. What is Open-Meteo?Free, open-source weather API providing ERA5 reanalysis + NWP forecast data globally.
Q42. What is GLO-30 DEM?Copernicus Global 30m Digital Elevation Model — released by ESA, freely available.
Q43. What is a .cbm file?CatBoost binary model file storing trained model weights.
Q44. What is Rasterio?Python library for reading/writing geospatial raster files (GeoTIFF). Used to read DEM, slope, SAR rasters.
Q45. What is EPSG:4326?Coordinate reference system for standard latitude/longitude (WGS84) — used for GPS coordinates.
Q46. What is EPSG:32646?UTM Zone 46N — projected CRS we transform to for accurate pixel lookups in Assam rasters.
Q47. What is rio-tiler?Library built on Rasterio for serving raster tiles via HTTP — used to render susceptibility map overlay.
Q48. What is Leaflet?Open-source JavaScript library for interactive web maps. We render the GIS map using React-Leaflet.
Q49. What is Vite?Fast build tool and dev server for React applications — replaces Create React App.
Q50. What is TailwindCSS?Utility-first CSS framework. We use v4 with Vite plugin for styling the expert dashboard.
